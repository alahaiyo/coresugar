# coresugar 内核崩溃分析

通过 coresugar MCP Tool 完成分析。由 Agent 选择调查方向，不让服务端代替推理。

## 输入和边界

- 使用用户提供的 Linux 绝对路径调用 `open_dump`，不自动上传、复制或采集 vmcore。
- `MISMATCH`、`INVALID` 或 crash 的版本不一致警告必须先解决，不能继续使用错误符号得出结论。
- `PARTIAL` 表示精确构建身份、源码或模块符号尚未完全验证。报告说明哪些判断受此影响。
- `source_identity` 是当前文件的哈希，不能据此声称源码与崩溃内核完全一致。
- 注意部分转储、缺失内存和 livepatch；补丁或模块栈需要相应源码和符号才能进一步解释。

## 调查方式

从 `sys`、`log`、`bt` 获取现场，先找到异常任务、CPU、指令地址和异常寄存器，再根据现有证据选择下一条命令。

支持的主要命令形式：

```text
sys
log
bt [-a|-f|-l|-p] [任务或地址]
ps [-m|-p|-l]
kmem -i
dis [-l|-r|-f] 符号或地址 [数量]
sym 符号或地址
whatis 类型
p 符号
struct 类型 地址
rd [-x|-d|-u] 地址 数量
```

不要使用 shell、脚本、任意 GDB 表达式或函数调用。`rd` 和 `dis` 数量最多 256，先用小范围查询。
完整任务表和所有 CPU 栈可能非常大，优先针对故障现场查询。命令允许的形式以实际返回为准。

`crash_exec` 默认命令超时 30 秒，客户端不能超过服务端配置的上限。超时或采集超限会关闭会话；重新打开后缩小调查范围，不假定原会话已经恢复。

### 证据和大输出

每次执行获得 `evidence_id`。`truncated` 仅表示响应截断；`capture_truncated` 表示完整输出没有全部采集，报告不得把该证据当作完整输出。

用 `get_evidence` 的 `offset` 和 `limit` 分页；使用返回的 `next_offset`，不要根据字符数计算字节偏移。
`complete` 表示已到保存内容的末尾，仍需检查 `capture_truncated`。出现 `output_base64` 时，精确重组应解码该字段。
日志过大时先读取元信息，再查询尾部或相关页，不必将所有任务和内存内容送入上下文。

使用 `search_source` 找函数，再用 `read_source` 读取相对路径和行号。搜索是字面量、按行匹配；目录应尽量缩小。
两种源码操作也返回证据编号。搜索被截断时，“未找到”不能作为函数不存在的证据。
源码路径禁止 `..`、未配置的绝对路径和符号链接；编译路径须先按管理员配置的映射转换。

## 调查过程总结

每次分析都必须通过 `record_analysis_step` 保存可读的调查过程总结，程序将按顺序编号
写入会话目录下的 `analysis-summary.md`。它与最终崩溃报告分开，用于回顾操作和调整程序。

- 每完成一轮有意义的调查就提交一次，不逐条翻译命令流水，也不等到结束才补写。
- `title` 是通俗的步骤名称，例如“查看调用栈和寄存器”。
- `summary` 简述实际做了什么、发现了什么、哪些问题仍未确认，以及下一步准备验证什么。
  不记录内部思维过程，不把计划执行的操作写成已经执行。
- `evidence_ids` 引用本会话实际证据，服务端会校验存在性。外部材料准备等没有 MCP 证据的
  操作可以不填，但必须说明是外部操作；服务端不会自动核实这段文字。
- 结束前提交一条“本轮结果与停止原因”：明确是谁或什么限制决定停止、尚未执行哪些调查，
  以及是否确实需要用户补充资料。不要把测试流程结束或样本不足当成现有 case 根因已查清。
- 意外断连后可针对原会话补写，接口支持会话关闭及服务重启后的追加。

例如，读取 `bt` 和反汇编后提交：

```json
{
  "session_id": "cs-实际会话编号",
  "title": "检查故障指令和寄存器",
  "summary": "执行 bt 和 dis，发现故障指令是 div %rcx，RCX 为 0，确认直接原因是除零。尚未确认这个零值如何形成，下一步核对变量和相关内存对象。",
  "evidence_ids": ["ev-bt的实际编号", "ev-dis的实际编号"]
}
```

程序保留 `operations.jsonl` 作为原始记录，不根据命令名自动编造上述发现。

## 报告

记录输入身份和校验状态，然后分别写明：

- 已确认事实：引用命令、证据编号和关键输出位置。
- 直接原因：用故障指令、寄存器和异常类型解释当时为何崩溃。
- 根因判断：给出推导链和置信程度；调用栈上的函数不自动等于根因。
- 尚未确认的信息：例如源码版本、模块符号、转储缺失或变量的形成过程。
- 下一步调查：指出补充哪些资料或命令可以验证剩余假设。

只有实际存在且能够通过 `get_evidence` 读取的编号可以引用。普通错误输出也是证据，但不是成功读取的内核状态。
结束分析后调用 `close_dump`；证据可以在关闭或服务重启后查询。
